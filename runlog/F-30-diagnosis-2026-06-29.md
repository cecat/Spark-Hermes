# F-30 diagnosis — `response_url` POST failures from the live Hermes gateway

**Date:** 2026-06-29 (continuation of the day's session)
**Symptom (carried forward from prior session):** Slack `/hermes` slash commands reach
the gateway and execute, but the result POST to the Slack-issued
`response_url` (`https://hooks.slack.com/commands/...`) fails. User sees
"Running /hermes…" forever; gateway log shows:

```
WARNING gateway.platforms.slack: [Slack] response_url POST failed:
Cannot connect to host hooks.slack.com:443 ssl:default
[Temporary failure in name resolution]
```

The prior session's hypothesis: OpenShell L7 proxy preset for `hooks.slack.com`
with `request_body_credential_rewrite: true` mangles the unauthenticated
callback POST, with aiohttp surfacing the rejection as a DNS error.

## Environment

- Host: spark-960b (Linux 6.17.0-1014-nvidia, aarch64)
- NemoClaw 0.1.0 / Hermes v2026.5.16
- Container: `openshell-gandalf-354307c9-7df4-47a5-9b86-f6ae0a81ae9e`
- Sandbox netns: `sandbox-b5d7c459`
- Gateway Python: `/opt/hermes/.venv/bin/python` (3.13), `aiohttp 3.13.4`,
  no `aiodns`/`pycares` (so aiohttp uses `ThreadedResolver`, i.e. a
  threadpool wrapper around `socket.getaddrinfo`)
- Container DNS: `/etc/resolv.conf` → `127.0.0.11` (Docker embedded),
  forwarding to host `10.0.4.1`
- L7 proxy: `http://10.200.0.1:3128`; gateway env sets
  `HTTPS_PROXY`/`http_proxy`/`https_proxy`/`ALL_PROXY` to it, but
  `aiohttp.ClientSession()` is created with default `trust_env=False` in
  the failing call site, so it does **not** honor those env vars. (Transparent
  egress through the L7 proxy is wired at the netns level by some mechanism
  outside iptables — the netns's nat table is empty — so traffic still
  reaches the proxy regardless.)

## Call site (upstream Hermes, unmodified)

`/opt/hermes/gateway/platforms/slack.py:485` (verified pristine, no Spark
patches):

```python
try:
    async with aiohttp.ClientSession() as session:        # fresh session per POST
        async with session.post(
            ctx["response_url"],
            json=payload,                                  # {"response_type":"ephemeral","replace_original":True,"text":...}
            timeout=aiohttp.ClientTimeout(total=10),
        ) as resp:
            if resp.status == 200:
                return SendResult(success=True, message_id=None)
            body = await resp.text()
            logger.warning("[Slack] response_url POST returned %s: %s", resp.status, body[:200])
except Exception as e:
    logger.warning("[Slack] response_url POST failed: %s", e)
# Non-fatal — the user saw the initial ack already.
return SendResult(success=True, message_id=None)
```

Each call creates a brand-new `ClientSession` (and therefore a brand-new
`TCPConnector` and a brand-new DNS lookup). No retry, no DNS cache reuse.
The exception is logged as a `WARNING` and swallowed — the function returns
`success=True` regardless, so Hermes never tries a fallback (e.g. delivering
the result via Socket Mode).

## What I tested

### Test 1 — reproduce the call from a fresh subprocess in the same context

Ran the *identical* `aiohttp.ClientSession().post(...)` against
`https://hooks.slack.com/commands/T0/0/test` from a Python subprocess
invoked with `docker exec -u sandbox`, using the same venv, the same uid,
and (implicitly) the same netns/DNS as the gateway:

```
trust_env=False STATUS=404 BODY[:120]='no_team'
trust_env=True  STATUS=404 BODY[:120]='no_team'
```

`404 no_team` is the **correct** Slack response for a fabricated URL — it
means the request reached Slack's hooks endpoint and was processed.
Both `trust_env=True` (using HTTPS_PROXY) and `trust_env=False` (direct,
matching the live gateway's call) succeed.

### Test 2 — long-lived loop, multiple sequential POSTs, 30s wait

To rule out "first call works, later calls fail":

```
#0 status=404 body='no_team' dt=0.13s
#1 status=404 body='no_team' dt=0.13s
#2 status=404 body='no_team' dt=0.12s
sleeping 30s with same loop alive...
after-sleep status=404 body='no_team'
```

All four succeed. The mode of failure described in the handoff did not
reproduce.

### Test 3 — historical evidence in `/sandbox/.hermes/logs/`

The "Cannot connect to host hooks.slack.com:443 ssl:default [Temporary

```

```

The current container start is `2026-06-29 18:48:08Z`, `restartCount=3`.
Live `/tmp/gateway.log` has had no `response_url` errors in the ~45 minutes

### Test 4 — confirm DNS resolver in use

`aiohttp.resolver.DefaultResolver` = `ThreadedResolver`. No `aiodns`
installed, so this is a thread-pool wrapper around glibc `getaddrinfo`.
The error message `[Temporary failure in name resolution]` is exactly
glibc's `EAI_AGAIN` (`gaierror(-3, ...)`), surfaced through
`aiohttp.client_exceptions.ClientConnectorDNSError`.

### Test 5 — examine the L7 proxy preset

`/opt/nemoclaw-blueprint/policies/presets/slack.yaml` declares
`hooks.slack.com` exactly the same way as `slack.com` and `api.slack.com`
— same `request_body_credential_rewrite: true`, same allow rule for
POST `/**`. If `request_body_credential_rewrite` were the root cause,
`slack.com`/`api.slack.com` POSTs would fail too — and they don't (Socket
Mode handshake POSTs to `slack.com/api/apps.connections.open` succeed and
Hermes uses it constantly).

## What the evidence actually says

1. **The proxy/policy hypothesis is unsupported.** The L7 proxy preset
   treats `hooks.slack.com` identically to other Slack hosts that work
   reliably, and `request_body_credential_rewrite` is not a credible cause
   for an error that arrives as `EAI_AGAIN` from the resolver layer
   *before* any TCP connection is attempted.

2. **The failures cluster on intermittent EAI_AGAIN events**, not on a
   per-host policy decision. EAI_AGAIN is glibc's "DNS server returned
   SERVFAIL or timed out" response, which is consistent with Docker's
   embedded `127.0.0.11` resolver hiccupping under load or briefly losing
   upstream (10.0.4.1 → host resolver). It is **not** consistent with the
   L7 proxy returning HTTP-layer denials — those would surface as `403`
   responses or connection-reset errors, not `gaierror -3`.

3. **The call site amplifies the impact** in two ways:
   - A fresh `ClientSession` (and a fresh DNS lookup) per call means there
     is no DNS cache to reuse a known-good answer.
   - The single failed lookup is swallowed silently: no retry, and the
     function returns `success=True` so Hermes doesn't fall back to Socket
     Mode.

   So a single transient EAI_AGAIN — which would be invisible if there
   were even a one-shot retry — causes the user-visible "Running /hermes…
   forever" symptom and a misleading "non-fatal" log line.

4. **The intermittency explains why the prior session saw consistent
   failure and I see none.** Slash commands haven't been issued in the
   ~45 min since the current gateway PID started; nothing in the
   reproduction harness is producing the load that historically correlated
   with the failures. The failure is real (logs are explicit), but it is
   not reproducible on demand and it is not deterministic per host.

## What a clean fix looks like

Two upstream-Hermes-clean fixes; either or both. Neither involves Spark-side
patches, custom policy YAML, or runtime monkey-patches:

### Option A — add a one-shot retry on transient DNS failure

In `gateway/platforms/slack.py:485`, wrap the POST in a small retry loop
that catches `aiohttp.ClientConnectorDNSError` (or, more narrowly,
inspects the chained `OSError.errno == -3` / `socket.gaierror`). One
extra attempt with a 250 ms backoff would eliminate the user-visible
symptom for every EAI_AGAIN observed so far. Two lines of code; upstream
PR-able.

### Option B — fall back to Socket Mode delivery if response_url POST fails

The function currently logs "non-fatal" and returns `success=True`. That
is incorrect: the *user* did not receive the result. Hermes already holds
an open Socket Mode connection to Slack and a `channel_id`/`user_id`
context for the slash invoker. On `response_url` POST failure, post an
ephemeral message via `chat.postEphemeral` (or a regular message in DMs)
through the Socket Mode `AsyncWebClient` that's already initialized.
That's also an upstream Hermes change.

A is the smaller, more targeted patch and would fully close the symptom.
B is the more defensive change and would also protect against future
incidents where `hooks.slack.com` is genuinely unreachable (Slack
incidents, network partitions). Doing both upstream is cheap.

## What I am explicitly **not** recommending

- **No custom egress preset** for `hooks.slack.com`. The proxy is not the
  cause; adding a Spark-side YAML to "fix" something that isn't broken
  there would just accrue maintenance debt that breaks on every NemoClaw
  release.
- **No monkey-patch** of `gateway/run.py` or `slack.py` in
  `/opt/hermes/`. Container restarts wipe the writable layer (per F-C in
  the handoff) and any patch would silently disappear.
- **No `requests`-as-sync-shim** in place of aiohttp. That's the kind of
  jury rig the operator wants to avoid.

## Open questions worth flagging to a reviewer

1. **Why has `127.0.0.11` been intermittently flaky?** The handoff's F-35
   notes one unexplained container restart on 2026-06-27; restartCount is
   now 3. If Docker's embedded resolver or upstream `10.0.4.1` is dropping
   queries under load — for any reason — that's an environmental issue
   that will bite other code paths beyond `response_url`. Worth a deeper
   look at the host resolver and any rate-limiting on the internal DNS.
2. **Is there a host-side mechanism for transparent egress that bypasses
   `iptables` nat?** The sandbox netns has empty NAT tables but traffic
   still reaches the L7 proxy at `10.200.0.1:3128`. This is presumably
   eBPF or a veth-level router installed by `openshell-sandbox`. Worth
   confirming so future debugging starts from accurate mental model.
3. **Should `aiohttp` ever be used directly in Hermes adapters, or should
   everything route through `httpx` + the existing OpenShell-aware
   `OpenshellResolveSession`?** A handful of call sites use raw aiohttp
   (this is one). Standardizing would reduce surprises.

## Suggested next steps (for the operator to decide)

1. **File an upstream Hermes issue** with this diagnosis + a one-line
   patch for Option A. Optionally a follow-up PR for Option B. This is the
   "no jury-rig, maintainable" path and survives all NemoClaw upgrades.
2. **In the meantime**, accept that `/hermes` slash commands may
   occasionally hang on "Running /hermes…" until the upstream fix lands.
   `/sethome` is already worked around by writing the env var directly
   (and that's no longer a workaround — that's the supported path now
   that the symptom is understood not to require source patches).
3. **Investigate F-35 (container restarts) and the embedded-DNS
   intermittency independently** — both because they have wider impact
   than just `response_url`, and because reducing DNS flakiness reduces
   the load on whatever retry logic Hermes ultimately gains.
